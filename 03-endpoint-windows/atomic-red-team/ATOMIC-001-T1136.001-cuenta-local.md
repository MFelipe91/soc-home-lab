# ATOMIC-001 · Creación de cuenta local (T1136.001)

| | |
|---|---|
| **Técnica** | T1136.001 · Create Account: Local Account |
| **Táctica** | Persistence |
| **Prueba** | Atomic Red Team `T1136.001-4` · *Create a new user in a command prompt* |
| **Equipo** | `WIN11-ENDPOINT` (192.168.56.30), usuario `analista`, integridad High |
| **Fecha** | 04-11-2026, 15:30 (hora de Chile) |
| **Resultado** | **Detectado** por 2 fuentes independientes (Sysmon y registro de Seguridad de Windows) |

## Qué simula

Un atacante que ya tiene acceso al equipo se crea una cuenta local para volver a entrar después, aunque le quiten el acceso original. Es una forma básica de persistencia.

Comando ejecutado por la prueba:

```text
net user /add "T1136.001_CMD" "T1136.001_CMD!"
```

Limpieza prevista por la propia prueba: `net user /del "T1136.001_CMD"`.

## Lectura de analista

- **Dos fuentes para un mismo hecho.** Sysmon cuenta el *cómo* (cadena de procesos y comando exacto) y el registro de Seguridad confirma el *qué* (la cuenta se creó de verdad). Con una sola fuente podría ser un intento fallido; con las dos hay confirmación.
- **Credencial en texto plano en el log.** La contraseña de la cuenta nueva aparece completa en `commandLine`. Cualquiera con acceso al SIEM la ve. En un caso real habría que tratarla como credencial expuesta y limitar quién puede leer esos eventos.
- **La regla 92040 es la que importa.** Tiene nivel 12, mapeo MITRE correcto (T1136.001) y envía correo. Las reglas 92052 y 92036 son de contexto y por sí solas serían ruido.
- **Ruido propio de la preparación del laboratorio.** Antes del ataque aparecieron unas 15 alertas de nivel 15 (regla 92213, *Executable file dropped in folder commonly used by malware*) al instalar el módulo `powershell-yaml` y los scripts de Atomic Red Team, más la auditoría CIS (reglas 19005 y 19014). Son falsos positivos causados por mis propias herramientas y no se mezclan con el análisis del ataque.

## Respuesta recomendada si esto fuera real

1. Confirmar con el usuario `analista` si creó esa cuenta. Si no, tratar el equipo como comprometido.
2. Aislar el equipo, deshabilitar la cuenta nueva y revisar su pertenencia a grupos (la alerta 60170 indica que entró al grupo Users).
3. Buscar el origen: qué proceso lanzó la cadena PowerShell → cmd y cuándo empezó la sesión (`logonId 0x581ef`).
4. Rotar las credenciales del usuario `analista` y revisar otras cuentas nuevas con `net user`.

## Limpieza

Cuenta `T1136.001_CMD` eliminada con `net user /del "T1136.001_CMD"` y verificada con `net user` (la cuenta ya no figura en la lista).
