# ATOMIC-003 · Borrado de registros de eventos (T1070.001)

| | |
|---|---|
| **Técnica** | T1070.001 · Indicator Removal: Clear Windows Event Logs |
| **Táctica** | Defense Evasion |
| **Prueba** | Simulación **manual** con `wevtutil` (no existe el archivo de Atomic Red Team para esta técnica en la ruta estándar: dio 404 dos veces) |
| **Equipo** | `WIN11-ENDPOINT` (192.168.56.30), usuario `analista`, integridad High |
| **Fechas** | 04-11-2026 (registro de Seguridad) y 05-11-2026 (registro de Aplicación), hora de Chile |
| **Resultado** | Windows avisó con baja severidad; el comando **no estaba cubierto**. Brecha cerrada con una **regla propia** (100100, nivel 12) |

## Qué simula

Un atacante que ya ejecutó acciones en el equipo borra los registros de eventos para ocultar lo que hizo. Se usa `wevtutil`, herramienta legítima de Windows (`cl` = *clear log*).

Comandos ejecutados, en PowerShell como administrador:

```text
wevtutil cl Security
wevtutil cl Application
```

## Ejecución 1 (04-11, 18:33): detección parcial

Se borró el registro de Seguridad (`wevtutil cl Security`).

| Fuente | Qué pasó |
|---|---|
| Windows | Generó el evento **1102** ("The audit log was cleared"). No se puede evitar: es el propio sistema el que anota que alguien vació el registro |
| Wazuh, regla de fábrica **63103** | Alerta de **nivel 5**: *The audit log was cleared*. MITRE **T1070** (Indicator Removal), Defense Evasion |
| Sysmon | Registró la creación del proceso `wevtutil.exe` (comprobado en el equipo con `Get-WinEvent`) |
| Wazuh, alerta por el comando | **Ninguna.** Las búsquedas por `commandLine:*wevtutil*` y `image:*wevtutil.exe` no devolvieron resultados |

Alerta 63103, campos relevantes:

| Campo | Valor |
|---|---|
| `rule.id` / `rule.level` | 63103 / 5 |
| `rule.groups` | windows, windows_logs, log_clearing_auditlog |
| `rule.mitre.id` | T1070 (técnica padre, no la sub-técnica T1070.001) |
| `data.win.system.eventID` | 1102 |
| `data.win.system.providerName` | Microsoft-Windows-Eventlog |
| `data.win.logFileCleared.subjectUserName` | analista |
| `data.win.logFileCleared.subjectLogonId` | 0x581ef |

**Brecha:** Sysmon tenía el comando completo, con proceso padre y usuario, pero ninguna regla lo interpretaba. Solo existía el aviso genérico del propio Windows, y únicamente para el registro de Seguridad.

## Corrección: regla propia 100100

Se agregó una regla en el servidor Wazuh (`/var/ossec/etc/rules/local_rules.xml`) que parte de la regla base de Sysmon *Process created* (61603):

```xml
<group name="windows,sysmon,defense_evasion,">
  <rule id="100100" level="12">
    <if_sid>61603</if_sid>
    <field name="win.eventdata.image" type="pcre2">(?i)\\wevtutil\.exe$</field>
    <field name="win.eventdata.commandLine" type="pcre2">(?i)\b(cl|clear-log)\b</field>
    <description>Event log cleared with wevtutil (possible log tampering)</description>
    <mitre>
      <id>T1070.001</id>
    </mitre>
  </rule>
</group>
```

Archivo de la regla: [`reglas-wazuh/100100-wevtutil-borrado-registros.xml`](../../reglas-wazuh/100100-wevtutil-borrado-registros.xml).

Pasos seguidos (en el servidor Wazuh, por SSH desde el anfitrión):

1. Verificar que la regla base 61603 existe y que el número 100100 está libre.
2. Agregar la regla al final de `local_rules.xml`.
3. Validar la configuración con `wazuh-analysisd -t` (sin errores).
4. Reiniciar con `wazuh-control restart`.

## Lectura de analista

- **La detección por resultado y por comando son cosas distintas.** El evento 1102 avisa que el registro de Seguridad *ya fue* vaciado y solo para ese registro. La regla 100100 mira el **comando**, así que cubre cualquier registro que se intente borrar con `wevtutil`, con el usuario, el proceso padre y la ruta.
- **El nivel de fábrica es bajo para algo muy raro de ver en uso legítimo.** Borrar registros casi nunca ocurre en operación normal. La regla de fábrica lo deja en nivel 5; la regla propia lo sube a 12.
- **Hallazgo de infraestructura: desfase de reloj entre el servidor Wazuh y el endpoint.** En la ejecución 1 la alerta quedó marcada a las 18:27:55 y el evento original a las 18:33:50 (unos 6 minutos de diferencia). En la ejecución 2 la alerta marca 16:00:46 y el evento de Sysmon 16:01:54 (cerca de 1 minuto). En un SOC real los relojes se sincronizan con NTP: un desfase estropea las líneas de tiempo y la correlación.
- **Mapeo MITRE de fábrica a nivel padre.** La regla 63103 usa T1070. La sub-técnica T1070.001 la aporta la regla propia.
- **Limitación de la regla:** busca `wevtutil` con `cl` o `clear-log`. No cubre otras formas de borrar registros, como `Clear-EventLog` en PowerShell.

## Mejoras propuestas (no implementadas)

1. Regla equivalente para `Clear-EventLog` y `Remove-EventLog` de PowerShell.
2. Sincronizar el reloj del servidor Wazuh y de la VM con NTP.
3. Correlacionar en una sola alerta el evento 1102 con el comando de Sysmon que lo causó.

## Respuesta recomendada si esto fuera real

1. Tratar el equipo como comprometido: nadie borra los registros sin motivo.
2. Aislar el equipo y conservar la evidencia. Lo ya enviado al SIEM sigue disponible aunque el registro local esté vacío.
3. Identificar quién lo ejecutó (`analista`, sesión `0x581ef`) y desde qué proceso padre.
4. Revisar en el SIEM la actividad anterior del mismo usuario y equipo: lo que el atacante quiso ocultar se hizo antes del borrado.

## Limpieza

El borrado de registros no se puede deshacer. En este laboratorio no tiene impacto: la evidencia está en las capturas y en Wazuh, y Windows empieza a registrar de nuevo desde cero.
