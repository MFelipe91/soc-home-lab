# ATOMIC-002 · Tarea programada para persistencia (T1053.005)

| | |
|---|---|
| **Técnica** | T1053.005 · Scheduled Task/Job: Scheduled Task |
| **Tácticas** | Execution, Persistence, Privilege Escalation |
| **Prueba** | Atomic Red Team `T1053.005-2` · *Scheduled task Local* |
| **Equipo** | `WIN11-ENDPOINT` (192.168.56.30), usuario `analista`, integridad High |
| **Fecha** | 04-11-2026 (ejecuciones a las 17:11 y 17:44, hora de Chile) |
| **Resultado** | Primera ejecución: Windows **no registró** la creación de la tarea (brecha de visibilidad). Tras activar la auditoría: **detectada** por 2 fuentes |

## Qué simula

Un atacante deja programada la ejecución de un programa para que corra solo más tarde, o en cada inicio de sesión, y así mantiene el acceso aunque se reinicie el equipo. `schtasks.exe` es una herramienta legítima de Windows, por eso los atacantes la usan: se mezcla con la actividad normal.

Comando ejecutado por la prueba:

```text
SCHTASKS /Create /SC ONCE /TN spawn /TR C:\windows\system32\cmd.exe /ST 20:10
```

| Parte | Significado |
|---|---|
| `/Create` | Crear una tarea |
| `/SC ONCE` | Una sola vez |
| `/TN spawn` | Nombre de la tarea |
| `/TR C:\windows\system32\cmd.exe` | Programa que ejecutará |
| `/ST 20:10` | Hora de inicio |

Limpieza de la prueba: `SCHTASKS /Delete /TN spawn /F`.

## Ejecución 1 (17:11): detección parcial

Sysmon registró el proceso y Wazuh alertó con la regla 92032. Pero al buscar el evento de Windows **4698** (tarea programada creada) en Wazuh no hubo resultados, y en el equipo `Get-WinEvent` con `Id=4698` en el registro de Seguridad respondió *No events were found*. La tarea sí existía (`schtasks /Query /TN spawn` la mostraba en estado `Ready`).

**Brecha:** Windows no estaba auditando la creación de tareas programadas, así que ninguna herramienta podía verla en el registro de Seguridad.

## Corrección aplicada

Se activó la subcategoría de auditoría *Other Object Access Events* (en el equipo `WIN11-ENDPOINT`, PowerShell como administrador):

```powershell
auditpol /set /subcategory:"Other Object Access Events" /success:enable /failure:enable
auditpol /get /subcategory:"Other Object Access Events"
```

El segundo comando confirmó `Success and Failure`. Luego se borró la tarea (`SCHTASKS /Delete /TN spawn /F`) y se repitió la prueba.

## Ejecución 2 (17:44): detección completa

| Hora UTC | Regla | Nivel | Descripción | MITRE | Fuente |
|---|---|---|---|---|---|
| 20:44:07.026 | **92032** | 3 | Suspicious Windows cmd shell execution | T1059.003, T1087 | Sysmon (evento 1) |
| 20:44:07.089 | **60228** | 4 | A scheduled task was created | **T1053** (Execution, Persistence, Privilege Escalation) | Seguridad de Windows (evento 4698) |

Los dos eventos ocurren con **63 milisegundos** de diferencia, y eso confirma que el comando de Sysmon es el que creó la tarea.

## Lectura de analista

- **La visibilidad depende de la configuración del endpoint.** Wazuh no se equivocó: el evento no existía porque Windows no lo generaba. Cambiar una política de auditoría pasó de "no se ve nada" a "alerta con MITRE".
- **Dos alertas débiles que juntas son fuertes.** La 92032 (nivel 3) y la 60228 (nivel 4) son bajas por separado. Cuando coinciden en el mismo segundo, con el mismo equipo y usuario, cuentan la historia completa: quién, con qué comando y qué quedó creado.
- **El mapeo MITRE no es exacto.** La regla 92032 mapea a T1059.003 (intérprete de comandos), correcto, y a T1087 (descubrimiento de cuentas), que no describe esta actividad: es un mapeo genérico de la regla. La regla 60228 mapea a la técnica padre T1053, no a la sub-técnica T1053.005. La técnica exacta la determina el analista leyendo el comando.
- **El nivel es bajo para una persistencia.** Cualquier tarea nueva genera nivel 4, sea de un instalador legítimo o de un atacante.

## Mejora propuesta (no implementada todavía)

Regla propia que suba la severidad cuando una tarea programada nueva ejecuta `cmd.exe`, `powershell.exe` u otro programa ubicado en `Temp` o `AppData`, o cuando `schtasks /Create` se lanza desde un `cmd /c`. Un binario legítimo de un instalador rara vez cumple eso.

## Respuesta recomendada si esto fuera real

1. Listar tareas recientes (`schtasks /Query /V /FO LIST`) y comparar con una línea base.
2. Revisar el programa que ejecuta la tarea y su hash.
3. Identificar el proceso padre y cómo se llegó a esa sesión.
4. Eliminar la tarea y buscar otras persistencias (claves de registro, servicios, otras cuentas).

## Limpieza

Tarea `spawn` eliminada con `SCHTASKS /Delete /TN spawn /F` y verificada con `schtasks /Query /TN spawn`.
